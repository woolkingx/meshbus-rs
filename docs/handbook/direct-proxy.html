Direct Proxy Foundation

Direct proxy is the native path where sources, services, compatibility adapters, and future peers express session intent directly to mesh-bus.

Thesis

source intent -> metadata enrichment -> rule/policy -> scheduler -> exit | service | upstream peer

Speed matters, but the first goal is cleaner rule and policy decisions. Event pipeline decides. Data plane moves. Observers sample. Compatibility protocols only project into this shape.

Direct proxy is the bottom product layer that must be correct before mesh transport optimization, chain, multi-hop, striping, reorder, or transport fast paths can be product claims.

Transparent TPROXY/TUN capture is an advanced gateway mode. It is not required for the MVP because normal users can configure SOCKS5 or HTTP proxy explicitly, and reverse proxy targets are configured by the operator.

Source Lease Rotate Scheduler

Status: source implementation and owner tests are local-green; live deployment and observation label projection remain. The owner is mesh-bus-scheduler-loadbalance. Core still filters candidates by capability, route_group, target sink, and health before the scheduler runs.

source_key
  + core SourceActivity { active_flows, idle_since_ms }
  -> SourceLease { exit_id, created_at_ms, last_seen_at_ms, generation, cooldown_until_ms }
  -> weighted rendezvous hash(source_key, generation, candidate_id)
  -> ordered ScheduleDecision(chosen exit first, fallbacks after)
AxisContract
InputRankContext.source_key, RankContext.source_activity, healthy filtered candidates, configured weights, and scheduler-owned clock. The default key scope is source-only; target_key must not participate in the daily-use key.
State ownerThe loadbalance scheduler owns one lease table per scheduler instance: source_key -> SourceLease. The kernel owns active flow_pin preservation; the scheduler only selects for new flow opens.
SelectionIf no lease exists, the leased exit is absent, or the leased exit is unhealthy, select by weighted rendezvous hash over the current candidate set. Otherwise daily mode keeps the leased exit until core reports true source idle long enough to expire the lease.
Idle rotationidle_timeout_secs expires the source lease only after core reports source_activity.active_flows == 0 and now - idle_since_ms reaches the configured window. The next new flow reselects; active flows are never force-moved.
Max ageDaily default is max_age_policy=off, so active sources rotate only on idle/unhealthy. soft lets the next new flow advance generation after max_age_secs and cooldown, but it may land on the same exit. hard must choose a different healthy exit when one exists; use soft/hard for validation or deliberate distribution, not as the daily default.
Why not source-targetModern pages open many self-check, CDN, API, telemetry, and asset connections to different targets. A source-target key splits one user page across exits and breaks the stable-exit property the daily mode needs.
ObservationLogs/metrics must expose selected sink, peer_id, source lease generation, lease reason (new, hit, idle_expired, max_age_soft, max_age_hard, unhealthy), route_group, close reason, and failure delta without inspecting payload.
scheduler:
  kind: LoadBalance
  mode: source-lease-rotate
  source_lease_rotate:
    key_scope: source
    idle_timeout_secs: 600
    max_age_secs: 3600
    max_age_policy: off
    switch_cooldown_secs: 60

Data Movement Contract

movement -> source intent -> bus session -> direct path proof

Timing must separate source wait, pipeline/rule time, scheduler time, egress/service open time, movement time, return/write wait, and close propagation.

Stream candidates are direct halves, Tokio copy, std copy, blocking splice where Linux endpoints allow it, and future sockmap only after a direct single pinned stream is proven. Datagram candidates are persistent session, normal UDP send/recv baseline, future packet loop, sendmmsg/recvmmsg, and GSO/GRO.

EventBus must not move payload bytes.

Observation Contract

observation -> source intent -> bus session -> direct path proof

Every direct path must emit or preserve source id, target/service id, selected sink, route_group, operation, bytes/datagrams in and out, close reason, path evidence, and compatibility adapter id when applicable.

Implementation Order

implementation-order -> source intent -> bus session -> direct path proof
  1. Keep proven direct TCP reverse and SOCKS5-over-Mesh paths as the MVP baseline.
  2. Keep UDP reverse service semantics and product e2e green.
  3. Keep HTTP CONNECT forward ingress green as the general-user compatibility adapter.
  4. Add operator examples for reverse TCP, reverse UDP, SOCKS5 forward, and HTTP CONNECT forward.
  5. Run fresh local and two-node live smoke for every MVP lane.
  6. Only after those gates, revisit transparent gateway capture and L7 HTTPX plugins.

Do not reorder this so mesh fast paths, TPROXY/TUN, or L7 HTTP routing block the product MVP.

Non-Goals

non-goals -> source intent -> bus session -> direct path proof

Do not implement HTTP semantic routing, HTTPS interception, HTTP/3 semantic proxying, VMess, XRAY, TLS termination, HTTP path/header inspection, decrypted TLS inspection, or raw payload inspection in the foundation path. HTTP CONNECT is allowed as an edge adapter because it only projects target intent and then relays opaque bytes. Do not invent full service discovery before local service routing is proven. Do not claim production mesh from loopback-only direct tests.
