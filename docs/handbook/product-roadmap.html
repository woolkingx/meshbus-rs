Product Roadmap

mesh-bus is an OSI-aware Rust transport substrate for programmable direct proxy and mesh transport. Compatibility protocols are edge plugins; native direct session routing is the product skeleton.

Position

mesh-bus is not SOCKS5, HTTP CONNECT, VMess, XRAY, a VPN replacement, a Kubernetes service mesh, or a QUIC wrapper. Those protocols and deployments are adapters or bindings over the bus.

source intent -> local bus session -> encrypted events -> N:N paths -> logical endpoint reconstruction

The product value is mesh-aware session routing, adjacent-peer capability exchange, path observation, programmable exit selection, encrypted event delivery, and native direct byte/datagram movement.

The product should feel like a modern mesh proxy fabric with Squid-like parent-peer composition, but without becoming HTTP-cache centered, proxy-protocol centered, or a tunnel wrapper.

Run 2: Multi-Exit Fabric

Run 2 turns the proven single remote exit path into a modern Squid-like mesh proxy fabric: one or more client-facing SOCKS5 gateways select from an upstream mesh-bus pool, and every pool node may also accept local clients directly.

Architecture v4: the mature product shape is gateway plus upstream mesh-bus pool. Compatibility protocols remain ingress/egress adapters; the product core is encrypted L4/L5 session fabric with operator-visible path evidence.

client(SOCKS5)
  -> mesh-bus gateway node
       owns: local access, rule, route_group, scheduler, health decision
  -> upstream mesh-bus pool
       owns: MeshPeerUdp ingress, MeshSec open, local TCP/UDP/SOCKS5/service egress
  -> server

Default Run 2 port profile: use port number 2080 for pool nodes: 2080/udp is MeshPeerUdp with MeshSec, and 2080/tcp is the optional direct SOCKS5 client entry. The shared number is an operator convention; TCP and UDP remain separate L4 owners and separate listeners.

The first Run 2 claim is multi-entry, multi-exit session fabric, not full automatic cluster routing. Private-lab proof has exercised one gateway across a five-node MeshSec pool with even round-robin distribution and zero gateway dispatch failures; daily-use mode returns to session-sticky selection to keep web sites on a stable exit. Dynamic discovery, cluster-wide topology control, remote mutation, and true multipath striping remain future work.

Market Position

The first product wedge is a programmable L4/L5 substrate for teams building direct proxy, private mesh transport, edge gateways, and auditable traffic-control systems. The user buys control over session intent, policy, scheduling, observation, and transport evidence without having to make a compatibility protocol the product core.

Encrypted N:N Event Fabric

The native mesh model is not a tunnel and not a channel. A logical stream or datagram flow may be decomposed into encrypted MeshEvents, sent through multiple peers, ports, and paths, and reconstructed at the logical endpoint by L5 semantics.

ConceptProduct rule
EventThe basic mesh protocol unit. Stream chunks, datagrams, control, route adverts, capability adverts, and samples are event families.
EnvelopeL6 protection around a MeshEvent. WAN profile exposes only delivery hints and ciphertext.
Port/pathL4 delivery coordinate. It never becomes session identity or service identity.
EndpointL5 owner that deduplicates, reorders, reassembles, and closes logical session meaning.

Compatibility Boundary

SOCKS5, HTTP CONNECT, DNS, VMess, XRAY, Shadowsocks-like protocols, and transparent capture adapters must decode only at the edge, project intent into session request fields, preserve close reasons and observation labels, and prove their own protocol compatibility.

They must not put protocol parsers in core, claim native-path performance, or define the product skeleton.

Fast Movement Contract

StreamDatagramObservation
Prefer direct stream halves after scheduling. Use splice where Linux TCP endpoints allow it. For mesh transport, represent stream as ordered events reconstructed by L5 endpoints. Keep EventBus out of payload movement. Use persistent datagram sessions. Preserve one logical datagram per message. For mesh transport, datagrams are encrypted events that may replicate across paths and deduplicate at the endpoint. Event pipeline decides. Data plane moves. Observers sample. Scheduler consumes path evidence. No layer owns another layer's schema.

First Implementation Slice

  1. Define direct source schema for stream and datagram intent.
  2. Add direct stream source and direct datagram source to runtime config.
  3. Add local e2e comparing direct stream against SOCKS5 CONNECT and direct datagram against SOCKS5 UDP ASSOCIATE.
  4. Define direct stream service capability and add direct reverse e2e.
  5. Record throughput, close reason, timing, and metrics label differences.

Functional status: the direct stream source, direct datagram source, stream/datagram service sinks, route_group selection, SOCKS5 forward, HTTP CONNECT forward, and secure two-node product fixtures are proven by binary e2e. The live 198.51.100.36 service slice now has repeatable SOCKS5 HTTPS acceptance, Operator metrics delta, MeshSec packet capture/fail-closed proof, journal audit, operations fault probes, and a release throughput baseline. Fine-grained bus-internal timing, long-run soak, and optional HTTP CONNECT/UDP DNS live client probes remain measurement work.

Run 2 status: private-lab live proof now covers gateway selection across five MeshPeerUdp exits, direct pool-node SOCKS5 entry, encrypted MeshSec movement, per-peer operator counters, and zero gateway dispatch failure during the observed run. The remaining gates are failed-peer avoidance for new sessions, health-aware sticky reselection, and long-run soak.

Non-Goals

Do not rename the product around direct proxy. Do not parse SOCKS5, VMess, XRAY, HTTP, DNS, or decrypted TLS in core. Do not treat QUIC connection state, UDP port, socket, or channel state as route truth or session truth. Do not claim production N:N from loopback-only tests.
