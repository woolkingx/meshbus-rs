System Architecture

The core is an event-pipeline kernel plus reusable L4/L5/L6 transport substrate. It is not a proxy core, packet-router clone, protocol parser, DNS server, or application service mesh.

Kernel Thesis

source -> pipeline graph -> sink

Kernel primitives are Event, TypedMap, Hook, Pipeline, Verdict, and KernelRegistry. Product names such as rule, scheduler, DNS, SOCKS5, resolver, proxy, and mesh peer are represented as sources, sinks, hooks, metadata fields, and wiring.

The executable substrate is an event-pipeline. OSI and TCP/IP remain owner maps: L4 places information onto paths, L5 owns logical sessions, L6 owns representation and transforms, and L7 projects external protocol intent.

OSI Event Fabric

mesh-bus follows OSI ownership instead of collapsing session, transport, encryption, and routing into a TCP/IP socket model. A socket, port, channel, QUIC connection, or peer link is delivery substrate only.

OSI is an owner map, not a stack diagram. Each layer owns the smallest fact it can prove, and every layer treats the facts above it as opaque. This is the rule that keeps mesh-bus from turning into a proxy protocol, VPN tunnel, or ad-hoc packet router.

LayerOwnsMust not own
L7 applicationExternal intent projection: SOCKS5, direct source, service, future HTTP, DNS, or capture adapter.Core routing truth or byte movement.
L6 presentationEncoding, encryption envelope, fragmentation, compression, checksum, parity, and payload transforms.Scheduler decision or session identity.
L5 sessionSession id, event sequence, dedup, reorder, reassembly, reliability policy, close semantics, endpoint reconstruction.Transport path ownership.
L4 transportPath, peer, port pool, route_group filtering, capability matching, health/cost scoring, replication, striping, delivery coordinates.Application semantics or decrypted payload inspection.
L3-ish adjacencyAdjacent peer visibility, hop ttl, path_trace, capability advertisement, policy evidence.Full topology or global route truth.
L2/L1 substrateUDP/IP/kernel/NIC delivery.Session identity.

The mesh form of this model is an encrypted event fabric: logical sessions decompose into events, events can be distributed across multiple peers/ports/paths, and the logical endpoint reconstructs meaning.

A layer names the API surface a participant implements, not a runtime tier. Any L6 transform may be used by any L7 adapter, any L5 session shape may be selected by any L7 adapter, and any L4 dispatch mode may be applied to any compatible session.

OSI Data Ontology

The OSI core is data ownership. In OSI terms, a layer receives an upper-layer service data unit (SDU), adds its own protocol control information (PCI), and produces this layer's protocol data unit (PDU). The PDU is the native data unit owned and processed by that layer; the SDU carried inside it stays opaque to that layer except for declared service boundaries.

PDU(layer N) = PCI(layer N) + SDU(from layer N+1)
TermMeaning in mesh-busOwnership rule
SDUData received from the layer above, such as encoded payload, session unit, or application bytes.Carry it as opaque data unless a declared owner exposes a typed surface.
PCIThe fields and state this layer adds to do its job: path labels, session ids, transform descriptors, crypto counters, protocol control fields.This is the layer's native owned data. Only this owner mutates it.
PDUThe complete data unit for this layer: this layer's PCI plus the carried SDU.This is the layer's CRUD boundary and state-machine unit.

Architecture starts by asking what data exists and who owns it. Logic, modules, state machines, errors, timeouts, observers, and fast paths all follow from that ownership. A module is the implementation boundary of a data owner, not a place to hide scattered behavior.

The machine-checkable review frame is the two-axis data/control matrix schema: one axis names layer and protocol family ownership; the other names data, control, evidence, lifecycle, and backpressure flow crossings. A row is valid only when it names owned PCI, carried SDU, schema owner, code owner, and proof gate.

LayerNative owned dataCarried SDU rule
L7 applicationProtocol syntax, credentials, application intent, rule input context, external request state.Stitches L6 codec, L5 control, and L4 transport surfaces into one application behavior.
L6 presentationCodec state, transform descriptor, envelope header, key epoch, replay window, padding, checksum/compression state.Treats application payload meaning as opaque while transforming representation.
L5 sessionSession id, lifecycle, flow semantics, return semantics, ordering, close reason, endpoint reconstruction.Treats transformed payload units as opaque data carried by the session.
L4 transportFlow id, path, route_group, sink candidate, health/cost evidence, dispatch mode, path trace, transport handle.Treats session payload and application meaning as opaque; it may route only from L4-owned or declared metadata.

Opacity is not deliberate forgetting. It is pure ownership: a lower layer cannot read upward-owned data. For example, L4 routing must not inspect URL, SNI, host headers, SOCKS5 fields, or decrypted payload because those are not L4-owned data. Frame.payload is physically carried by core but semantically owned by the transform or application participant that produced it.

Some values separate owner, exposer, and value-origin. When they differ, the schema and handbook must say so. For example, flow_id is L4-owned, session_id and lifecycle are L5-owned, TransformDescriptor is L6-owned, and host:port intent, credentials, and RuleCtx are L7-owned. A rule may decide a route label from L7-owned input, but the resulting candidate filter remains L4-owned data.

Source concepts: SDU/PCI/PDU encapsulation, OSI data movement.

Metadata Contract

Metadata is the only cross-hook communication surface. The stable namespaces are `net.*`, `transport.*`, `policy.*`, `auth.*`, `trace.*`, and schema-registered `ext.*` fields.

`route_group` is metadata used to filter sink candidates. `PipelineId` is control flow. They must not collapse into one concept.

Protocol-specific aliases such as SOCKS5 command names are compatibility fields. New adapters should populate generic metadata such as ext.operation first.

Rule Engine

The rule engine is a small declarative decision primitive. It receives a flat optional `RuleCtx`, evaluates first-match-wins rules, and returns a single `Action` such as allow, deny, set route group, set schedule hint, set transform, compose, or cost bias.

InvariantReason
`mb-rule` does not depend on `mesh-bus-core` or adapter crates.Rules are DTO-level policy, not kernel implementation.
Kernel does not depend on `mb-rule`.Kernel only sees typed request fields such as `route_group`.
No action inspects payload bytes.Policy describes routing, lifecycle, transform intent, not byte content.
Unsupported actions are no-op at a hook site and logged.One action union can serve multiple planes without forcing every site to consume every action.

Inside the forward pipeline, unsupported actions are stricter than library evaluation: resolver-pool and transform actions do not silently continue at policy.rule_chain; the hook fails closed because its declared writes are route group, schedule hint, fanout count, and cost bias.

Rule configuration is closed and explicit: rules are ordered, first match wins, default action is mandatory, empty string/set/composite predicates are invalid, route-group labels are non-empty, and compose conflicts are rejected at validation time.

Forward Pipeline

source Event -> net.resolve_or_recover -> net.enrich_geo_asn -> policy.rule_chain -> transport.pick_sink_cake -> Verdict::Accept(SinkId) | Reject | Drop

A source adapter creates an event from protocol input and projected metadata, then invokes the protocol-neutral pipeline runtime. For SOCKS5, CONNECT runs the pipeline once per session open; UDP relay packets run it once per target-bearing datagram; UDP ASSOCIATE control does not run the forward pipeline because no target exists yet.

Machine contract: mesh-bus-pipeline-hooks/schema.json owns the hook/runtime metadata boundary for SharedHookCtx, PipelineRuntime, hook templates, and exit-candidate projection.

Registry Verification

kernel-registry -> owned primitive -> legal boundary -> registry/proof gate

`KernelRegistry` validates sources, sinks, hooks, pipelines, wiring, IDs, hook functions, accept/jump declarations, DAG shape, namespace access, unsatisfied reads, side-effect restrictions, and unknown sinks before the bus starts.

End-of-pipeline `Continue` is invalid. Pipeline jumps must form a DAG. Runtime `Accept` and `Jump` payloads are checked against the hook declaration.

Verification also protects source wiring as a total single-valued function: every registered source has exactly one wiring entry, and no source appears twice. Hook namespace patterns are not wildcards; declared reads and writes must be covered by explicit namespace patterns.

Schema-Compiled Runtime

Schema, config, and rule files are compile inputs, not prose beside the code. Runtime build validates them into typed models, then compiles IDs, groups, capabilities, pipelines, observers, and candidate filters into compact executor tables.

The executor may still expose logical string IDs at APIs, logs, snapshots, and schema boundaries. Internally, hot paths prefer slots, enums, masks, arrays, atomics, and function pointers.

Async and Observation

async-observation -> owned primitive -> legal boundary -> registry/proof gate

Hooks are sync function pointers. Async upstream work, such as DNS resolver calls, crosses the boundary only through scoped shared hook context and a Tokio handle. Hooks must not spawn persistent tasks, hold state across hook boundaries, or keep locks around pipeline progress.

The data plane emits only declared observation facts. The canonical contract is Dataplane and Observation: core lifecycle/path facts use core.*, owner facts such as MeshSec/native drops use obs.*, and counters/path samples use declared pull sources. Metrics, Prometheus, exit-health updates, Operator snapshots, and CAKE feedback are projections rather than inline dispatch logic. Dispatch remains pick -> send -> emit.

Boundary Rules

boundaries -> owned primitive -> legal boundary -> registry/proof gate
  • Core depends on no L7 protocol crate.
  • Routing decisions use request metadata and path evidence, not protocol syntax or payload bytes.
  • `Frame.payload` is opaque bytes.
  • New L7 protocol means a new adapter pair, never a branch in core.
  • Async hook work uses the sanctioned scoped runtime bridge; hooks must not spawn persistent tasks or keep state across boundaries.
  • DNS is a resolver/enrichment hook for bus decisions, not an active port-53 listener in the core architecture.
  • Compatibility adapters may preserve protocol detail for logs, but core and scheduler decisions stay protocol-neutral.
