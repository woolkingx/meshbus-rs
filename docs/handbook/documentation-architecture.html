Documentation Architecture

This chapter defines how mesh-bus documentation is created, linked, and kept from fragmenting across handbook HTML, handbook/spec machine contracts, docs/plan, CLAUDE.md, schema.json, code, and tests.

Hierarchy

HTML handbook = topologic / logic schema -> schema.json = data / structure schema -> docs/plan = active task decomposition -> CLAUDE.md = execution rules and navigation -> code = implementation -> tests, e2e, and live proof

The handbook is not prose around the system; it is the topologic and logic schema of the system. It owns node/edge relationships, owner boundaries, allowed transitions, invariants, acceptance gates, and canonical links. schema.json owns data and structure shape: field contracts, protocol/config structures, samples, constants, and machine-verifiable constraints. Code may implement only the topology plus data shape represented by those two layers.

Authoring Rules

authoring-rules -> artifact role -> owning layer -> documentation gate
  • Topology, ownership, transition, invariant, or acceptance-gate changes start in the HTML handbook.
  • Data shape, field, enum, constant, sample, or machine-validation changes start in schema.json.
  • docs/ has only two durable documentation branches: docs/handbook for architecture/spec truth and docs/plan for runnable work plans.
  • Formal spec artifacts belong under docs/handbook/spec; a top-level docs/spec directory is forbidden.
  • CLAUDE.md files are execution rules, keypoints, and navigation; they are not architecture/spec sources.
  • docs/handbook/task-plans.html owns active plan status and dependency order.
  • docs/plan files are active action plans; they must link to handbook sections and only decompose work.
  • Old Markdown specs or plan drafts can provide source material, but after absorption the handbook must say the durable thing directly.
  • New config or protocol shape must update schema before code claims support.
  • Module CLAUDE.md files stay short: scope, keypoints, invariants, commands, links.
  • Tests must cite the acceptance gate they prove.

CLAUDE.md Role

claudemd-role -> artifact role -> owning layer -> documentation gate

Keep: scope, keypoints, local invariants, local commands, current canonical links, short decision summary.

Every module or guide CLAUDE.md carries one local design-rule: block. That block is the boot-card guard that says handbook owns topology/logic, schema owns data shape, and the directory may mutate only its owned PCI/data while carried SDU remains opaque.

Remove over time: full architecture, duplicated spec, long plan tasks, schema prose duplication, stale decision history.

Root CLAUDE.md remains the boot card. This handbook is the architecture/spec source.

When conflicts appear, handbook/spec defines architecture, docs/plan defines active task order, CLAUDE.md defines execution constraints, schema defines machine contracts, code shows implementation, and tests define proof.

Integration Sequence

integration-sequence -> artifact role -> owning layer -> documentation gate
  1. Handbook spine exists: index plus this documentation architecture chapter.
  2. Product roadmap, direct proxy foundation, system architecture, Mesh Protocol, dataplane observation, transport, compatibility, and testing gates exist as handbook chapters.
  3. Absorb useful status, process, and gate content from old Markdown drafts into owning handbook chapters.
  4. Back-link each section to schema, code owners, and tests during the next schema-sync pass.
  5. Add every multi-step work item to the task plan control chapter before execution.
  6. Trim CLAUDE.md files after each section is represented in the handbook.
