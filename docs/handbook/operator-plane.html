Operator Plane

The Operator Plane is the system management interface for config, status, metrics, probes, deployment, and future admin control. It is an adapter over existing owners, not the data plane, control plane, or mesh protocol.

Thesis

Data Plane
  client traffic -> ingress -> bus session/frame -> egress -> upstream

Control Plane
  event -> hooks -> rule -> scheduler -> verdict

Operator Plane
  human/tool -> Operator API -> config/status/metrics/probe/deploy owners
             -> CLI client
             -> Web client
             -> future remote admin client

The management surface must be API-first. CLI and Web UI are clients of the same Operator API. They must not each grow their own config parser, runtime reader, probe runner, or service controller.

Plane Boundary

PlaneOwnsMust not
Data PlaneOpaque stream bytes and datagrams after a path is selected.Parse operator commands, mutate config, or run management probes outside normal ingress/egress paths.
Control PlaneEvent metadata, hook execution, rule decisions, scheduler verdicts.Move payload bytes, own systemd, or expose an admin API directly.
Operator PlaneOperator intent, config inspection, validation, status, metrics snapshots, probes, deployment actions, and admin audit.Become route truth, bypass core path, mutate dispatch internals, or become Mesh Protocol.

Operator actions can control hooks, rules, config, and service lifecycle through owner APIs. They cannot become hidden branches inside core dispatch or scheduler code.

Service Control Loop

When mesh-bus is operated as a service, the Operator Plane is the control loop around the running substrate. It reads owner state, validates intended changes, applies only through the owning adapter, and records evidence. It does not become the data plane.

operator intent
  -> read current owner data
  -> validate intended data
  -> dry-run owner operation
  -> apply through owner boundary
  -> observe metrics/log deltas
  -> emit audit/diagnose evidence

Probe Contract

Operator probes are production questions expressed as normal traffic. A probe may choose an ingress adapter, target, timeout, and expected route group; it must not call dispatch internals, mutate route state, or decode opaque SDU bytes after the protocol adapter has projected target intent.

probe request
  -> Operator API request schema
  -> configured ingress listener
  -> normal control-plane verdict
  -> normal L4/L5/L6 data movement
  -> metrics snapshot delta
  -> probe response
ProbeInput dataNormal path proofResponse fields
SOCKS5 connecttarget URI or host:port, timeout, optional route_group expectation.SOCKS5 handshake enters the configured SOCKS5 ingress and opens a stream session through the same pipeline as a client.ok, route_group, close_reason, dispatch_success_delta, dispatch_failure_delta, duration_ms.
HTTP CONNECTauthority target, timeout, optional route_group expectation.CONNECT request enters the configured HTTP CONNECT ingress and then relays opaque stream bytes.ok, route_group, close_reason, dispatch_success_delta, dispatch_failure_delta, duration_ms.
UDP DNSDNS server target, query name, timeout, optional route_group expectation.UDP ingress sends one datagram through the configured datagram path and receives a response through return semantics.ok, route_group, close_reason, datagram_success_delta, dispatch_failure_delta, duration_ms.
Mesh peerpeer id or route_group, timeout, optional target service.Uses a public local ingress or service sink over MeshPeerUdp/MeshSec; it never sends a private test packet directly into the mesh-peer crate.ok, peer_id, route_group, close_reason, dispatch deltas, MeshSec drop deltas when available.

A successful probe proves only the selected path and time window. It does not declare global mesh health, WAN performance, or protocol completeness.

Diagnose Bundle Contract

A diagnose bundle is a redacted evidence object for support and self-operation. It composes existing owners and host adapters; it is not a second telemetry backend.

  -> Operator API
       -> status owner
       -> metrics owner
       -> config redaction owner
       -> host process/socket adapter
       -> journal tail adapter
  -> redacted artifact

ConfigRuntime config ownerredacted effective config and schema version.PSK, SOCKS5 password, bearer token, private key material.

The bundle is complete only when it can be attached to a bug report without leaking production secrets. Exportable diagnose YAML is stricter than an interactive effective-config view: secret values and secret field markers such as static_key_hex must both be absent.

Safety Rules

RuleContract
Schema firstEvery request/response type belongs in an operator schema before code exists.
Read before writeM0/M1 must land before hot reload or remote mutation.
Dry-run before applyEvery write operation has a dry-run form and reports old/new fingerprints.
Audit every mutationWrite operations emit actor, target owner, old state, new state, gate id, and result.
No core shortcutsProbe and admin actions use public owner APIs or configured ingress/egress paths.
Remote write is MeshSec-onlyRemote admin cannot use debug-clear transport or unauthenticated HTTP.

Non-Goals

Do not make Operator API a new mesh protocol, core scheduler, policy language, or hidden dispatch surface. Do not let Web UI read config files, scrape raw logs as truth, mutate runtime maps, or bypass schema validation. Do not ship remote write before local read/probe/write gates are proven.
